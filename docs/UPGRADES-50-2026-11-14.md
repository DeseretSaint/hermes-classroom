# Fifty upgrades for Coursebook

*Written 2026-11-14 from four surveys of HEAD, each candidate verified against the code, then filtered against the 683 cards already on the board. Every item here names a failure a learner or operator can see, the line that causes it, the change, and a test that fails before it. The adversarial note is the argument against the item; entries that could not survive their own note were dropped.*

Companion: `docs/OSS-LANDSCAPE-2026-11-14.md` — seven of these fifty are "adopt this library at this seam" rather than "write it ourselves", and the other thirty-eight refusals are recorded there.

## Detail

### 1. An interrupted create leaves an empty plan and says start over

*resume · impact 4 · effort M · cinder*

**Symptom.** If jobs.create fails after course.create and enrolment.create, or the app closes during submit, the course is left with an empty draft plan row and no job. Reopening its Plan tab says 'No plan yet — This course has no plan attached. Start a new course to generate one', discarding the stored goal and choices.

**Evidence.** desktop/src/95-studio.js:6154-6156 — "title: 'No plan yet'" / "This course has no plan attached. Start a new course to generate one; nothing is invented to fill the gap."; desktop/src/50-create.js:456-465 returns "courseId, planId, enrollmentId" on a jobs.create failure; coursebook/domain.py:702-705 inserts the placeholder: "INSERT INTO plans ... VALUES (?, ?, 1, 'draft', NULL, '{}', ?, NULL)".

**Change.** When course.outline has a plan with zero objectives and jobs.list has no plan job, read course.get for the stored goal/recipe/dials/level/subject_domain/scope and render a 'Write this course's plan' action that calls jobs.create{kind:'plan', brief:{stage:'plan', course_id, enrollment_id, ...stored}} with idempotency key 'cb-plan-resume-<courseId>'. Replace the 'Start a new course' sentence with that action.

**Acceptance.** tests/test_desktop_w2_3_plan_truth.py::PlanWaitTruth::test_a_placeholder_plan_with_no_job_offers_to_write_it_again — renders a course with an empty draft plan and no jobs, asserts a resume control and that one press queues exactly one plan job with the stored scope; fails at HEAD because the empty state has no action.

**Against.** Partial creates are rare and the in-session banner already offers Try again, so a resume path adds a write route on an empty plan. But losing the app between course.create and jobs.create is exactly the close-the-app case the create copy invites, and the current screen tells the learner to create a second course, spending research twice.

### 2. A failed jobs.list read turns a running plan into No plan yet

*error states · impact 4 · effort S · cinder*

**Symptom.** When jobs.list errors or is unsupported, the Plan tab reads no plan job and shows 'No plan yet — This course has no plan attached. Start a new course to generate one' while the plan job may still be running.

**Evidence.** desktop/src/95-studio.js:6625-6630 reads jobs.list with no status check; :6648 — "const jobId = retryJobId || jobHint || (planJob && planJob.job_id) || null"; :6154-6156 — "title: 'No plan yet'" / "This course has no plan attached. Start a new course to generate one; nothing is invented to fill the gap."

**Change.** Handle jobs.status === 'error' (and !supports('jobs.list')) when plan/objectives are absent: render an ErrorState titled 'The plan's progress could not be read' with a Try again that reloads jobs and outline, and never fall through to the empty state.

**Acceptance.** tests/test_desktop_w2_3_plan_truth.py::PlanWaitTruth::test_a_jobs_list_error_is_never_presented_as_no_plan — mounts LearnerPlanView with outline.plan null and a jobs error; asserts the error copy and retry exist and 'This course has no plan attached' is absent; fails at HEAD.

**Against.** useRpcQuery retries and the error may be transient, so an error state could flash. But while it lasts the copy asserts the course has no plan and invites a duplicate course; a temporary error state is more honest than a false empty state.

### 3. Home offers Start on a section that has no lesson page yet

*returning learner · impact 4 · effort M · cinder*

**Symptom.** After approving a plan but before pressing Generate lessons, Home says 'Start <section>. Work through this section, then finish its check.' Pressing it opens a classroom with no authored page, because the next-step rule only checks for a parked page, not for a missing one.

**Evidence.** coursebook/domain.py:3001-3010 checks only lesson["state"] == "needs_review"; :3027-3030 — "if binding is None:" / "return {\"kind\": \"start_lesson\", \"label\": f\"Start {title}\"}"; desktop/src/30-home.js:2900 — "if (kind === 'start_lesson') return '. Work through this section, then finish its check.'"

**Change.** In _library_next_step, when _authored_lesson_identity returns None (or lesson_state is None), return a new kind 'write_lesson' with label 'Write the lesson for <title>' and the objective id; map it in the desk to open the course's Plan tab where Generate lessons lives. Only return start_lesson when an authored page exists.

**Acceptance.** tests/test_learner_plan_flow.py::LearnerPlanFlowTest::test_home_step_is_write_lesson_before_any_page_exists — builds an approved plan with one objective and no lesson rows, asserts next_step.kind == 'write_lesson'; tests/test_desktop_field_desk.py::FieldDeskRenderTest::test_write_lesson_opens_the_plan_tab asserts the control routes to Plan. Both fail at HEAD with start_lesson.

**Against.** A learner is expected to press Generate lessons immediately after approving, so Home's start step is only a shortcut. But the create result says the learner can leave the page, so returning Home is supported, and Start on a blank classroom is a false next step.

### 4. A scope-band refusal offers Try again, which cannot succeed

*scope bands · impact 4 · effort M · cinder*

**Symptom.** A short-course brief whose plan authors 12 objectives is refused as a scope-band failure; the learner sees 'Planning stopped before a plan was written', 'What happened: VALIDATION FAILED' and a Try again button that repeats the identical brief. The backend's own refusal names the legal scopes and says a second authoring pass cannot fix it.

**Evidence.** coursebook/generation.py:840-848 — "a second authoring pass cannot fix it" / "the honest answer is a typed refusal that names the legal bands and the learner's action, and **no plan row at all**"; :4787-4792 — "which scope {scope!r} does not hold" / "Legal scopes are:"; desktop/src/95-studio.js:4259-4283 — "title: ... 'Planning stopped before a plan was written'" / "action: { id: 'try_again', label: 'Try again' }".

**Change.** In planRejectView, branch on job.error.details.reason === 'scope_band' (the details are already copied into the job error by job_service.py:1044-1050). Return kind 'band' with a title such as 'This goal does not fit a short course', body naming details.objectives and details.objective_band, and a primary action 'Choose a different shape' that calls onChangeGoal with the same brief and scope set to details.legal_scopes[0]. Do not offer Try again when legal_scopes is non-empty.

**Acceptance.** tests/test_desktop_plan_reject.py::PlanRejectModelTest::test_a_scope_band_refusal_names_the_legal_shape_and_never_offers_try_again — model with error.details.reason 'scope_band', objectives 12, legal_scopes ['full'] yields kind 'band', action id 'change_shape', and onChangeGoal receives scope 'full'; fails at HEAD with kind 'failed' and action 'try_again'.

**Against.** A generic Try again could by chance author a smaller plan, so the refusal is not mathematically guaranteed to repeat. But the backend's own docstring says a second pass cannot fix a band miss and supplies legal_scopes for exactly this action; offering the wrong repair is worse than a low-probability retry.

### 5. Neither the trailhead nor the plan review shows the goal

*plan preview · impact 4 · effort S · cinder*

**Symptom.** On 'Your trailhead' the only statement of intent is the truncated course title; on plan review the header is 'Plan draft · v1' plus a truncated hash. The learner approves a goal they cannot see at either gate.

**Evidence.** desktop/src/50-create.js:1458-1511 renders data-cb-create-preview-title and facts for shape/sections/mode/depth/level/outcome, with no goal text; :563-564 — "if (base.length <= 64) return base" / "return `${base.slice(0, 61).trimEnd()}…`"; desktop/src/95-studio.js:6175-6176 — "jsx(PlanStateBadge, { plan })" / "children: `plan ${String(planHash || '').slice(0, 19)}…`".

**Change.** Add one shared goal/proof summary block, fed by splitComposedGoal on the job brief or the stored goal, and render it in both the create trailhead (data-cb-create-preview-goal) and the plan review header (data-cb-plan-goal). Clamp to two lines; the title stays the name, not the intent.

**Acceptance.** tests/test_desktop_create_flow.py::CreateFormInteractionTest::test_the_review_step_shows_the_goal_and_proof_it_will_send and tests/test_desktop_w2_3_plan_truth.py::LearnerPlanAdjust::test_the_plan_header_restates_the_goal — both assert the exact goal text is present at the approval gate; both fail at HEAD.

**Against.** The course title is derived from the goal and is editable, so the learner has seen the words. But it is clamped to 64 characters and the proof sentence is never in it; after a change-goal seed the title can also be stale. Approval is the one place the exact intent must be visible.

### 6. Full-course plan review has no units and no time estimate

*plan preview · impact 4 · effort M · cinder*

**Symptom.** A 30-objective full course in five units renders as one numbered list under 'OUTLINE AND ACTIVITIES'; the plan's time estimate, promised at create as 'the plan carries its own estimate once it exists', appears nowhere.

**Evidence.** desktop/src/95-studio.js:6357-6358 — "jsx(CbLabel, { children: `OUTLINE AND ACTIVITIES (${objectives.length})` })" / "...displayObjectives.map((objective, index) => {"; coursebook/domain.py:4645-4647 serves "units": units but :4638-4648 has no time_estimate; coursebook/generation.py:12604 stores "\"time_estimate\": plan.get(\"time_estimate\")"; desktop/src/50-create.js:146 — "the plan carries its own estimate once it exists."

**Change.** Add time_estimate (from plans.schedule_json) to course.outline.plan as an additive field and render it as 'About N weeks' beside the plan state. When plan.units has more than one unit, group the objective rows under unit title headings instead of one flat list.

**Acceptance.** tests/test_learner_plan_flow.py::LearnerPlanFlowTest::test_course_outline_serves_the_plans_time_estimate asserts the field; tests/test_desktop_w2_3_plan_truth.py::LearnerPlanAdjust::test_a_full_plan_preview_groups_units_and_shows_the_time_estimate renders a two-unit plan with time_estimate and asserts both unit headings and 'weeks'. Both fail at HEAD.

**Against.** Units and time are planning aids, and the course path shows units after approval. But the plan gate is where 'planned in full' is approved; a flat 40-row list and no estimate makes that gate unreadable, and the create copy explicitly promises the estimate.

### 7. Plan review hides the exclusions the plan declares

*plan preview · impact 4 · effort M · cinder*

**Symptom.** The plan document records exclusions — what this course will not cover, including capabilities research could not support — but the plan preview never shows them. The learner can approve a course that silently drops part of the goal.

**Evidence.** coursebook/generation.py:12607 — "\"exclusions\": plan.get(\"exclusions\"),"; coursebook/domain.py:4638-4648 — the course.outline plan object carries "plan_id", "version", "state", "plan_hash", "validation" and "units" only; desktop/src/95-studio.js:6551-6567 shows sources and review notes with no exclusions line.

**Change.** Serve a bounded exclusions array in course.outline.plan and render a 'What this plan does not cover' list above the outline when it is non-empty, on both learner and parent plan review. Strip the two known rule prefixes ('Not covered — no supporting source:' and 'Scope shortfall — fewer supporting capabilities:') before display and keep the raw entries in a disclosure.

**Acceptance.** tests/test_desktop_w2_3_plan_truth.py::LearnerPlanAdjust::test_a_plan_with_disclosed_exclusions_shows_them_before_approve — fixture plan with two exclusions renders data-cb-plan-exclusions="2" and both stripped sentences; fails at HEAD because the field is neither served nor rendered.

**Against.** Exclusions can be rule-generated strings with internal prefixes, so showing them raw would leak pipeline words. But they are the plan's own disclosure of what it will not teach; strip the two known prefixes and show the bounded sentences, or the learner approves a narrower course unknowingly.

### 8. An approved plan offers no way to change the goal

*goal edit · impact 4 · effort S · cinder*

**Symptom.** After approval the only change control is 'Ask for a change', which immediately calls plan.replan with every objective kept (superseding the approved plan) and opens section editing. There is no way to say the goal itself was wrong; the onChangeGoal path exists but only a rejection can reach it.

**Evidence.** desktop/src/95-studio.js:5979-5981 — "objective_changes: objectives.map((objective) => ({ objective_id: objective.objective_id, change: 'keep' }))"; :6221-6224 — "onClick: startRevision" / "children: learner ? 'Ask for a change' : 'Start a new plan version'"; coursebook/domain.py:1301-1304 — "UPDATE plans SET state = 'superseded' WHERE course_id = ? AND state = 'approved'"; desktop/src/95-studio.js:6023-6034 shows the only onChangeGoal path is inside runPlanRepair for a rejection.

**Change.** On an approved learner plan, add a secondary 'Change the goal' action that confirms 'This starts a new course; this one and its evidence stay' and calls onChangeGoal with splitComposedGoal(plan goal), title, recipe, dials, locale, level, subject_domain and scope. Keep 'Ask for a change' for outline edits.

**Acceptance.** tests/test_desktop_w2_3_plan_truth.py::LearnerPlanAdjust::test_an_approved_plan_can_hand_its_goal_back_to_create — approved surface renders data-cb-plan-change-goal, clicking calls onChangeGoal with goal 'Learn Spanish' and outcome 'hold a conversation', and makes no plan.replan call; fails at HEAD.

**Against.** Changing a goal after evidence must not mutate the course or it would invalidate XP and checks; starting a new course is correct. The defect is that no affordance says so, and the only change button creates a version that cannot change the goal.

### 10. A rejected learner draft offers only Try again, not Adjust

*rejection · impact 4 · effort S · cinder*

**Symptom.** A learner's draft that failed an outline check offers only Try again, which re-runs the same brief; the action row hides 'Adjust this plan' whenever a rejection is shown. Editing a draft is supported and makes it approvable as manual review, but the learner cannot reach it from the refusal.

**Evidence.** desktop/src/95-studio.js:4318-4330 — for learner "action: learner ? { id: 'try_again', label: 'Try again' } : { id: 'edit_plan', label: 'Edit the plan' }"; :6181-6183 — "children: shownRejection && !editing ? null : ["; :5888 — "setRejectionHandled(true)" after saving an edit.

**Change.** For a learner and a kept structural or unsourced draft, make the primary action { id: 'edit_plan', label: 'Adjust this plan' } and call startEditing; keep Try again as the secondary. Keep change_goal for an empty draft and keep the manual-authoring label on the subsequent approval.

**Acceptance.** tests/test_desktop_plan_reject.py::PlanRejectModelTest::test_a_learner_structural_refusal_offers_adjusting_the_kept_draft — learner surface, structural reject, objectiveCount > 0 yields action id 'edit_plan'; tests/test_desktop_plan_reject.py::PlanRejectWiringTest::test_the_learner_adjust_action_opens_the_editor asserts startEditing runs and no jobs.create call is made. Both fail at HEAD.

**Against.** Manual editing bypasses the independent validator, and the panel deliberately routes learners to a fresh run. But the backend already supports manual authoring with an explicit 'not validated' label, and a repeated identical brief is the repair least likely to change a structural fault.

### 11. A transfer objective can be checked by a multiple-choice quiz

*transfer and application tasks · impact 4 · effort S · vellum*

**Symptom.** The one check family whose claim is "apply this to a case the lesson did not teach" is exempted from the kind map, so a three-choice scenario question passes every authoring gate and is graded by exact string match. The learner eliminates two options; nothing was applied. This is also the only transfer form that can ever reach a cold pass (see the production item), so the weaker form is the one that completes.

**Evidence.** coursebook/generation.py:8329-8331 — "elif declared_kind not in expected_kinds and not (", "declared_target == \"transfer\" and declared_kind == \"quiz\"", "):"; coursebook/generation.py:572 — "\"transfer\": (\"verification\", \"observation\"),"

**Change.** Drop the transfer-quiz exemption. Require transfer to be a verification artifact or observation, and when a quiz form is kept make it a typed constructed response over a case the page never worked, not an option pick. Enforce the same rule in plan validation (rule 5b) so a contradictory plan is refused before authoring.

**Acceptance.** tests/test_upgrade_transfer_kind.py::test_a_transfer_quiz_is_refused — before: enforce_lesson_rules accepts {kind: quiz, evidence_target: transfer}; after: it returns the named reason and refuses, while a transfer verification still passes.

**Against.** A scenario MC item with diagnostic distractors can probe transfer better than a checklist of "I did it" ticks, and the exemption exists because the rigorous verification form dead-ends in the ungradeable open lane. Removing the exemption without fixing that lane leaves transfer un-authorable, which is worse than a weak check.

### 12. The model segment prints the exact string the check keys

*lesson page / retrieval vs recognition · impact 4 · effort M · vellum*

**Symptom.** The only learner surface allowed to print the target is the model segment, and the check then keys that literal string with no rule that the check's prompt pose a case the page did not already solve. The learner reproduces a sentence read minutes earlier rather than producing the form in a new situation, so a recall-family check measures look-up plus short-term copying.

**Evidence.** coursebook/generation.py:5931-5933 — "clauses are scanned for on every learner surface except one. A segment with kind", "'model' is the one presentation surface: the target form, its reading or gloss and its", "function belong there."

**Change.** Require every check to state a new case (different interlocutor, setting or object) whose answer is the taught form, and add a deterministic gate: the check prompt and accepted answers may not reuse the model segment's sentence beyond the target form itself. Put the new-case requirement in the authoring directives next to the answer-leak rule.

**Acceptance.** tests/test_upgrade_new_case_check.py::test_a_check_that_reuses_the_model_sentence_is_refused — before: a draft whose prompt is the model sentence verbatim is accepted; after: it is refused with a named reason and a prompt that varies the case still passes.

**Against.** At L0 the form must be presented somewhere, and a hard new-case gate can produce unfair checks if the frame uses untaught vocabulary. Token-overlap gates are also easy to defeat with synonyms, so the gate may refuse good drafts while passing paraphrased copies.

### 13. A miss never names the rule; the teaching turn is not told what failed

*grading feedback · impact 5 · effort M · vellum*

**Symptom.** A wrong answer comes back as "not yet" with "does not match an accepted answer" or "outside tolerance by 0.5", and the pane prints exactly that string. The continuation prompt the teaching chat receives carries the verdict, the next action, the evidence class and an objective id — never the criteria — so neither the page nor the tutor can say which rule was missed or what to do differently.

**Evidence.** coursebook/validators.py:271 — "return False, \"does not match an accepted answer\""; coursebook/turn.py:619-623 — "continuation_prompt(", "verdict=verdict,", "next_action=str(result.get(\"next_action\", \"continue\")),", "evidence_class=str(result.get(\"evidence_class\", \"cold\")),", "objective_id=objective_id,"; desktop/src/70-learning.js:830 — "children: item.observed || item.id"

**Change.** Give each check an authored rule/misconception per accepted-answer group; return a feedback block on any non-pass (rule missed, the learner's actual answer evidence, one next action); carry that block into continuation_prompt and render it above the retry control in AttemptVerdict.

**Acceptance.** tests/test_upgrade_miss_feedback.py::test_a_not_yet_result_carries_the_rule_and_the_next_action — before: a not_yet GradingResult has only a generic observed string and pre_turn's context has no criteria; after: the result carries the authored rule and the context includes it.

**Against.** An authored rule stated to a learner who then retries can leak the answer and convert the retry into a copy task, which is why the current design withholds it. A model-written diagnosis can also be wrong and teach the error, and per-check authoring cost rises.

### 14. One hint costs the whole attempt, and the authored policy never reaches the pane

*hint ladders · impact 5 · effort L · vellum*

**Symptom.** Assistance is a single binary event. The pane always shows "Ask for a hint" and "I saw the answer" whatever `assistance_policy` the check authored, because `check.get` never projects it; and any hint marks the next attempt `hinted`, so that attempt can never be independent. There is no rung between nothing and full contamination: a stuck learner either gets no help or loses the item's evidence value.

**Evidence.** coursebook/generation.py:3562 — "\"hint\": {\"type\": \"string\", \"enum\": [\"available\", \"after_attempt\", \"none\"]},"; coursebook/domain.py:4533 — "\"practice\": _practice_view(stored.get(\"practice\"))," (the stimulus projection carries no assistance_policy); coursebook/domain.py:1837 — "if assist is not None or _attempt_rows_before(connection, enrollment_id, check_id):"; desktop/src/70-learning.js:2659 — "'data-cb-assist': 'available',"

**Change.** Author a hint ladder per check (nudge, cue, partial worked step), project the policy on `check.get`, reveal one rung per press and record which rung was used. Keep the full independence penalty for the last rung; a first-rung cue can still require a later cold pass on a fresh item.

**Acceptance.** tests/test_upgrade_hint_ladder.py::test_a_none_policy_offers_no_hint_and_a_laddered_check_offers_one_rung — before: the pane's assist group renders with policy "none" and one press writes hinted; after: policy none hides the control and a laddered check advances one named rung per press.

### 17. Failures and hinted passes never enter the review queue

*spaced-review scheduling · impact 5 · effort M · vellum*

### 18. The review interval ignores how the pass was earned

*spaced-review scheduling · impact 4 · effort M · vellum*

**Symptom.** The due date is last pass plus a ladder rung chosen only by evidence target. A first-try cold pass and a pass that followed two misses, a hint and a retry receive the same next interval, so the scheduler's spacing claim is blind to difficulty and to how much help the item needed.

**Change.** Allocate the cell instead of letting the clause block spend it: split max_queries into a capability share, a sequencing share and a breadth share for deep, order the breadth questions ahead of the optional glossary/reference tail so truncation can only drop the least useful ones, and record queries_breadth_dropped on the run when the cell still binds.

**Acceptance.** tests/test_up_research_breadth.py::ResearchBreadthTest::test_five_clause_goal_keeps_breadth_questions — derive_queries for a five-clause goal at full/deep must contain the common-mistakes and examples markers (a unique phrase, not a count), while single/survey and recipe one_off query sets stay byte-identical to today.

**Against.** Every added or reordered query costs a search call (45 s bound) and can win a page slot a capability question would have used, which is why the capability-first order exists. ### 34. One timed-out validation pass discards thirteen answered passes

*validation · impact 4 · effort M · quill*

**Symptom.** A full plan fails and the learner is told the host was unavailable, even though thirteen of fourteen passes answered and the plan itself was fine. The retry pays for research and a whole re-author, and if the slow pass is slow again the course never completes.

**Evidence.** coursebook/generation.py:4356-4365 — the pool settles every pass and then raises the first error (`if first_error is not None:` … `raise first_error`); run_plan_job re-raises it after recording (`if first_failure is not None:` / `raise first_failure`, generation.py:12390-12391). **Change.** Retry the failed pass once inside the same attempt (same schema, same prompt version, its own bounded deadline and usage row), and only fail the stage if the retry also fails; record pass_retries on the validation record and size the call ceiling for one retry per pass.

**Acceptance.** tests/test_up_validation_pass_retry.py::ValidationPassRetryTest::test_one_timed_out_pass_is_retried_in_place — a validator that times out on pass 3 once and answers on the retry must produce a passing plan in attempt 1, with one pass_retries entry and no second authoring call; today the job fails with HOST_UNAVAILABLE.

**Against.** This raises the worst legal call count per attempt from 1 + passes to 1 + 2 x passes, and a budget that does not count it will abort a run behaving as designed — the CP-015e defect again. Size plan_calls for the retry in the same edit, or the fix buys a worse failure.

### 35. A failed unit batch throws away the sections that passed

*units · impact 4 · effort L · quill*

**Symptom.** A nine-minute unit comes back with two of five sections unacceptable and every section is discarded. The retry re-authors from scratch and pays again for the three that were fine, so a unit that keeps failing costs the same as one that keeps succeeding.

### 37. Nothing compares two sections' checks for a duplicate question

### 38. A plan that declares no visual need is adopted without a floor

### 40. Live job cost reads zero until the stage has already finished

*observability · impact 4 · effort S · quill*

### 41. The job deadline is shorter than the plan stage's legal worst path
