# Sentinel performance report — long content and 50+ objectives

**Candidate:** `b476738` (merge of CB-049; `git log -1` in `.worktrees/t_19da8432`)
**Date:** 2026-11-06
**Author:** Sentinel (adversarial QA) — independent rig, no product code changed.
**Verdict:** **PASS with one blocking defect (D1).** Performance at the maximum *legal* content size is
good across every measure. But a section file above the cb.rpc v6 segment cap imports cleanly and then
cannot be read at all — a correctness failure triggered by exactly the "long body content" case this
task was built to test.

### 1.3 What is measured, and how

* **Time to first render** — `Page.reload` on `#/coursebook`, then (a) `first-contentful-paint` from
  the paint timeline, (b) wall time until the route is mounted **and** course rows exist.
* **Interaction latency** — measured *inside* the renderer: `performance.now()` at the synthetic
  click, then two `requestAnimationFrame`s for input→paint, then a 16 ms poll until the pane's own
  content marker appears (e.g. `Open section`, `All tags`, `CURRENT OBJECTIVE`). No CDP round-trip in
  the timing.
* **Scroll smoothness** — rAF timestamp deltas during a scripted scroll. Because the display is
  175 Hz, a "dropped frame" is defined as a frame interval **> 2 × the measured idle cadence
  (11.4 ms)**; uncapped raw deltas alone would be meaningless.
* **Long tasks** — `PerformanceObserver({entryTypes:['longtask']})` (>50 ms main-thread blocks).
* **Memory** — `performance.memory.usedJSHeapSize` and renderer RSS (`ps` for the renderer whose
  `--user-data-dir` is the sentinel-perf userdata). The leak test forces GC via
  `HeapProfiler.collectGarbage` before each sample.

## 3. Defect D1 — long section imports, then cannot be read (BLOCKER)

**Severity:** blocker for any pack whose section file exceeds 8,000 characters.
**Where:** `coursebook/pack_flow.py::_write_lesson_page` writes the entire section markdown as **one**
`lesson_segments.text` value with no length check; `cb.rpc` v6 caps `segments[].text` at
`maxLength: 8000` (`contracts/rpc.v6.json:1895-1901`). The import succeeds, the pack is listed, and
every read of that objective fails.

### Reproduce (API — no UI needed)

```console
$ python3 docs/sentinel-perf/probe-lesson-limit.py
objective 1 (47,000-char section): ok=false
  INTERNAL_ERROR  path=segments/0/text  retryable=false
  "lesson.page produced a non-contract result: ... is too long"
objective 2 (2,144-char section):  ok=true  segments=2  segment_chars=[2144,126]
objective 3 (2,145-char section):  ok=true  segments=2  segment_chars=[2145,126]
```

Exhaustive check (`docs/sentinel-perf/verify-all-lessons.py`, result in
`results/lesson-readability.json`) reads **every** objective of both courses:

| course | objectives | readable | failed | where |
|---|---|---|---|---|
| `sentinel-long-60-legal` | 60 | **60** | 0 | — |
| `sentinel-long-55` (over-cap) | 55 | 53 | **2** | ordinal **1** and ordinal **55**, `segments/0/text`, `retryable:false` |

Same enrollment, same course, same wire version: only the two long sections fail. Expected: import refuses the
pack (or splits/validates the section) with a clear reason. Actual: import reports success
(`{"pack_id":"sentinel-long-55","course_id":"crs_ddb6…","revision":0}`), then the lesson page is dead.

### Reproduce (UI)

`docs/sentinel-perf/extras.mjs --course overcap` opens the 55-objective course, Textbook, first section:

```
This section could not be read
INTERNAL_ERROR: lesson.page produced a non-contract result: lesson.page handler returned a result
outside the contract at segments/0/text: '## Objective 1: register in context 1…' is too long
[Try again]     `pre` elements rendered: 0
```

Screenshot: `docs/sentinel-perf/shots/overcap-lesson-error.png`.

**Impact.** A learner-published pack with one long chapter is permanently unreadable and "Try again"
can never succeed. The pack schema itself allows section files up to 32 MB
(`max_single_file_bytes`), so nothing warns the author at authoring or import time. This is a
data-dependent permanent failure, not a slow render.

**Suggested owner:** backend/generation (Lattice/Sable) should reject at import (`pack.import`) with a
specific error naming the file and the cap, or split a section into ≤8,000-char segments; the contract
already permits up to 500 segments per lesson.

| pane switch median | ≤ 100 ms | 11 ms **PASS** |
| pane switch worst | ≤ 250 ms | 15 ms **PASS** |
| frame > 32 ms during navigation/scroll | 0 | 0 **PASS** |
| long task during a lesson open | ≤ 1 per action | 1 × 69 ms **PASS (with note)** |

| heap growth per mount/unmount cycle | ≤ 0.5 MB | −0.003 MB **PASS** |
| 200 % text / 460 px overflow | 0 px | 0 px **PASS** |
| any legal-size lesson readable | 100 % | 60/60 objectives **PASS** |
| any imported lesson readable | 100 % | **FAIL — D1** |

**Note on the 69 ms task.** Opening the 3,565-word lesson blocks the main thread once for 69 ms
(~12 frames at 175 Hz) — a visible hitch, not a freeze, and only on the largest legal lesson. It does
not repeat on scroll, on the second long lesson, or during navigation. Not a release blocker; worth
knowing if lesson bodies grow.

## 5. Measurement limits (so the numbers are not over-read)

1. **Refresh rate.** This host renders at 175 Hz; frame budgets are 5.7 ms, not 16.7 ms. A 12 ms frame
   is one dropped frame *here* while being fine on a 60 Hz laptop. All frame claims are relative to the
   measured cadence.
2. **`--disable-gpu`.** The rig runs without GPU compositing (same as the project's other live
   captures). Paint/composite cost on a GPU build will differ; main-thread JS cost will not.
3. **Index render timing.** `textbook-index.renderMs` (≈160 ms) is bounded by the harness poll interval
   (150 ms), so it over-reports the small case. The honest index/lesson numbers are the in-renderer
   content-ready times (11–14 ms for the 60-row list; 83 ms for the long lesson).
4. **Fixture text is synthetic** — deliberately repetitive prose plus real code/list/table markup. It
   exercises layout and the markdown renderer, not reading comprehension.
5. **No second window / no concurrency.** This run is single-window; two-window and concurrent-job
   behaviour is covered by the separate adversarial pass, not here.

---

## 6. What this run does *not* prove

* That a **pack author** can ship a 20,000-word chapter — they cannot: D1 blocks it above 8,000 chars
  per section file, and the product does not tell them.
* That a **multi-section objective** is discoverable: the textbook index shows one row per objective
  and the lesson pane renders all parts in sequence only after the row is opened. That matched the
  design in `UX_SPEC.md`; it is noted, not filed as a defect.
* Anything about generated (Parent Studio) lessons — only pack-backed courses were measured.

---

## 7. Conclusion

* **Long content inside the contract:** solid. 3,565 words, 22,098 characters, a code block, a list and
  a table render in 83 ms with 371 DOM nodes; scrolling is jank-free; 200 % text and 460 px do not
  overflow or clip; there is no memory leak across repeated open/close.
* **50+ objectives:** solid. A 60-objective course renders a 578-node index, switches panes in
  11–15 ms, and does not slow the cold path.
* **Long content beyond the contract:** broken (D1). This is the one release-relevant finding and it
  must be fixed before any pack with a long chapter is shipped as "supported".
